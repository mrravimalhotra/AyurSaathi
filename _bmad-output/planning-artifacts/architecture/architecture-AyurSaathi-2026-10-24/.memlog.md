- (decision) AD paradigm: database-enforced modular monolith. One Next.js app, domain modules per journey phase, row-level security is the authority on access, server actions perform writes. - (direction) Ravi chose tenant isolation by ONE SUPABASE PROJECT PER CLINIC (not shared tables with clinic_id). CONFLICT to resolve: PRD FR-4 (clinic isolation inside one database), FR-6 (cross-clinic tests), FR-48 (seed with two Clinics), glossary Clinic, and ADR-20 all assume shared tables with clinic_id
- (question) If one project per clinic: how does the app pick the project (one Vercel deployment per clinic with its own env vars, vs one app choosing a project per request)? How are migrations rolled out to every clinic project? Does the prototype acceptance 'no clinic can read another clinic's data' become deployment-level isolation rather than a database test?
- (decision) AD tenancy: deployment-per-clinic. One Supabase project and one Vercel deployment per clinic, same codebase, selected by environment variables. Every clinic-owned table STILL carries clinic_id and every row-level security policy checks it (defence in depth; keeps pooling clinics later possible). Chosen by Ravi. Prevents: shared mutable state across clinics at the infrastructure level; prevents policies that forget the clinic key
- (constraint) Consequence: migrations and seed must roll out to every clinic project; a manifest of clinic projects is needed. Prototype has one live clinic project (Ayurvedgram) plus local dev. PRD FR-4/FR-6/FR-48 remain valid because tests seed two clinic rows in one database
