- (decision) AD tenancy: deployment-per-clinic. One Supabase project and one Vercel deployment per clinic, same codebase, selected by environment variables. Every clinic-owned table STILL carries clinic_id and every row-level security policy checks it (defence in depth; keeps pooling clinics later possible). Chosen by Ravi. Prevents: shared mutable state across clinics at the infrastructure level; prevents policies that forget the clinic key
- (constraint) Consequence: migrations and seed must roll out to every clinic project; a manifest of clinic projects is needed. Prototype has one live clinic project (Ayurvedgram) plus local dev. PRD FR-4/FR-6/FR-48 remain valid because tests seed two clinic rows in one database

- (decision) AD project selection: one deployment per clinic. Same repo; each Vercel deployment's environment variables point to that clinic's Supabase project. No per-request project routing. Chosen by Ravi. Prevents: keys for several clinics in one runtime
- (decision) AD access claims: role and clinic_id are placed in the user's sign-in token by a Supabase auth hook; row-level security policies read them from the token via helper functions. Chosen by Ravi. Consequence: a role change applies at next token refresh; sign-out on role change. Prevents: policies that each query profiles differently
- (decision) AD scheduler: pg_cron in the database runs hourly and calls idempotent database functions (and queued notifications) for follow-up check-ins and reminders; unique keys on episode, template and date. Chosen by Ravi. Vercel cron is not used. Prevents: duplicate sends and dependence on Vercel plan cron limits
