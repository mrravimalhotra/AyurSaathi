# Adversarial Review: ARCHITECTURE-SPINE (AyurSaathi)

Method: for each hole, two developer units, each obeying every AD literally, build incompatible things. Spine not edited.

Verdict: the spine fixes the platform (RLS, token, Result shape) well but leaves every shared entity (check_ins, alerts/notifications, patients, visibility, phase) without a single owner, shape or write path, so parallel units will collide on exactly the entities the PRD journeys cross.

## H1 (Critical): check_ins has two owners, three creators, two uniqueness keys
- Units: U1 builds `care` (daily Check-in, FR-36, Review Queue FR-37, review FR-39). U2 builds `continuity` (follow-up Check-in FR-41/42).
- Clash: the Capability Map lists `check_ins` under both `care` and `continuity`; AD-6 says a module writes only its own tables. Both obey by each creating its own table or each its own columns on one table. FR-37 and FR-42 require follow-ups to enter the same Review Queue, so the queue (care) must read continuity data, which AD-6 allows only via exported functions, which neither exports. AD-10 adds a third creator: the pg_cron function that creates due Check-ins, keyed "episode, template and date". FR-36's key is one per episode per day. A daily Check-in and a follow-up on the same date then collide or double up. Also undefined: answers shape (jsonb vs columns), where Flag and its reason are stored (computed at submit vs at read; FR-38 says changing a rule changes what is flagged), and "date" (UTC date vs Patient-local date, AD-9). FR-39 "review" writes check_ins + notes + medicines in one screen, spanning care and continuity tables.
- Fix (new AD): one table `check_ins` owned by `care` (rename the module concern "check-ins") with `kind` in (`daily`, `follow_up`), `template_id`, `local_date` (Patient zone), `answers jsonb` validated by the Zod schema from settings, `flags jsonb` and `flagged bool` written by one `evaluate_flags` call at submit, `reviewed_by/at`. Unique key `(episode_id, kind, template_id, local_date)`. `continuity` owns only scheduling (`follow_up_schedules`) and calls care's exported `createDueCheckIn`; the cron function only calls that same SQL function. Review action is one transaction (a single Postgres function) covering note, medicine change and reviewed mark.

## H2 (Critical): Alerts have no owner; notifications are written by everyone with no shape
- Units: U1 builds `arrival` ("I have landed", "I need help", flight-edit alert, FR-29/30). U2 builds `notifications` and the needs-attention block (FR-9) on the patient list; U3 `continuity` pending Consultation Requests (FR-44).
- Clash: "Alert" is a PRD term but no table, module or ERD entity exists. U1 inserts rows into `notifications` addressed to coordinators; U2 builds needs-attention as a query over source tables (unreviewed flagged check-ins, pending requests) and ignores notifications; the landed event gets no source table at all. AD-6 forbids U1 writing U2's `notifications` table, yet AD-10 says "events write a row to notifications". ERD says `PROFILE receives NOTIFICATION`, but Patients are not profiles in the spine, so patient notifications (published Day Plan, Invite) have no valid recipient key. Role-broadcast ("the Coordinator") vs specific user is undefined; so are `type` values, payload shape, dedup key, and whether alerts are cleared when handled.
- Fix (new AD): `notifications` is written only via one exported SQL function `app.emit_event(event_type, recipient_kind, recipient_id|role, subject_ref, dedupe_key, payload)`; no module inserts directly. Closed event-type enum in `lib/validation`. Recipient is `user_id` (auth uid) for both Patients and Staff; role-broadcasts fan out to one row per user at emit time. Alerts are a view over `alerts` (a table owned by `notifications`, `kind`, `episode_id`, `resolved_at`) fed by emit_event; each source module resolves via the same function. Landed/help are stored as `arrival_events` rows owned by `arrival`.

## H3 (High): patients written by onboarding and patients; Invite impossible under AD-4; patient↔auth link undefined
- Units: U1 builds `onboarding` (FR-13..16, 19). U2 builds `patients` (record, episodes, list, duplicate search FR-15, time zone FR-47).
- Clash: Capability Map lists `patients` under both; AD-6 says only the owner writes. U1 inserts patients rows directly, U2 insists on a `createPatient` function and adds required columns U1 never sets (e.g. `timezone`, default from clinic). Drafts (FR-14: no account, no Invite): U1 stores a `patients` row with `status='draft'`, U2's list and search treat every patients row as real, so drafts show up in the Patient list and in duplicate matching. Consent: ERD says patient gives consents, map puts consents in onboarding. Invite (FR-19) needs creating an auth user and a link, which needs the admin API; AD-4 allows the service-role key only in scheduled jobs and admin scripts, and AD-5 says request handling uses the user's token. Both units obey, neither can ship Invite; one will quietly use the service key in a server action. `app.current_patient()` maps token to patient, but nothing says where `patients.auth_user_id` is set or who sets it.
- Fix (new AD): `patients` module is sole writer of `patients`, `episodes`, `phase_events`, `consents`; onboarding calls its exported `createPatient/saveDraft/finalise`. Drafts live in a separate `onboarding_drafts` table (jsonb, owned by onboarding) and become a patients row only on finalise. A single `SECURITY DEFINER` function `app.create_patient_account` (or one named server-only route) is the sole sanctioned privileged path for Invite; amend AD-4 to name it and require it to take `clinic_id` from the caller's token, never from input. State `patients.auth_user_id` and who sets it.

## H4 (High): "staff_only" and role names mean different things per table
- Units: U1 builds `care` (Notes, medicines, Day Plans). U2 builds `documents`/`assessment` and the patient-facing views.
- Clash: AD-8 covers only Notes, Assessments, Documents with values `shared|staff_only`. Day Plans (draft/published), Pickup/Accommodation, Medicines, Consultations, Check-ins each need a different patient-visibility rule and AD-8 says nothing. "Patient-safe views, not base tables, where columns differ" leaves it to each unit which columns, view names and whether views are `security_invoker`; a view without invoker semantics bypasses RLS (AD-12 lists only tables and buckets). PRD matrix: Admin "read" Notes and Coordinator "reads Shared Notes and never Staff-only", while Admin read is unqualified. U1 lets Admin read all Notes, U2 limits to shared, both literal. Role strings in the token are not enumerated anywhere: AD-3 says `role` and `app.current_role()`, PRD says Patient/Coordinator/Doctor/Admin (and "Staff" as umbrella). U1 writes `role in ('staff')`, U2 `role = 'coordinator'`. "read" vs "yes" in the PRD matrix is also only partly mappable to policies. Clinic Settings is one row (`CLINIC ||--|| CLINIC_SETTINGS`) but branding is Admin-write and flag rules are Doctor-write; column-level write rules unstated.
- Fix (new AD): token `role` is exactly one of `patient|coordinator|doctor|admin`; `app.is_staff()` is the only way to say "Staff". Add an authoritative capability matrix as a SQL-backed table-by-role policy spec (`supabase/policy-matrix.md` or a checked-in test fixture) that policies and pgTAP both read, with Admin on Notes/Assessments set explicitly (suggest: shared only, plus staff_only for doctor only). Extend AD-8 to every patient-visible table: `visibility` for Notes/Assessments/Documents, `status='published'` for Day Plans, and patient-safe views are `security_invoker` and covered by AD-12 alongside tables. Split settings into `clinic_settings_branding` and `clinic_settings_clinical` (or section-keyed rows) with separate policies.

## H5 (High): phase moves and multi-table actions have no atomic owner
- Units: U1 builds `planning` (Programme recorded, deposit paid, UJ-6 "each step moves the Episode to the next Phase"). U2 builds `patients` (FR-10 phase moves, history).
- Clash: `episodes.phase` is owned by `patients`; U1 must call the exported `movePhase`, which is a separate server-action transaction. Failure between the two leaves a Programme recorded with the Episode in the wrong Phase. U1 instead updates `episodes.phase` directly (it only passes `episode_id`; RLS allows Staff), writing no `phase_events`. Whether moves are auto (log a step) or manual (FR-10) is unstated; so are allowed transitions (back moves, skip for returning Patient FR-11). The same issue hits arrival (flight edit + alert + event), care publish (plan status + notification + idempotency) and Check-in review (H1). AD-5 idempotency keys: storage location, scope and expiry undefined, so each module invents its own table or column and "safe to run twice" varies.
- Fix (new AD): state mutations that touch more than one module's tables are single SQL functions (`app.move_phase`, `app.publish_day_plan`, `app.review_check_in`) called by the server action; `episodes.phase` is writable only through `app.move_phase` (column revoked from direct UPDATE, trigger writes `phase_events`). Define phase move rules (manual only in prototype, any phase to any, returning Patient starts at assessment/planning). One shared `idempotency_keys(clinic_id, user_id, action, key, result)` table and helper in `lib/db`, written in the same transaction.

## Lesser holes (not top five)
- AD-9: define "local date" for daily Check-in keys and Day Plan dates as the Patient-zone date, not UTC date; a unit using `date(created_at)` will break across zones.
- AD-12 does not cover views, SECURITY DEFINER functions, or the Storage bucket policy mirroring (tests on tables only); add functions and views to the "no test fails build" list.
- Conventions: soft delete `deleted_at` "where retention may apply" leaves each unit to decide; RLS and views must exclude deleted rows by one helper, or lists and counts differ.
- Money in minor units: currency exponents (JPY 0, INR 2) not specified; two units format differently.
- AD-7: Flag evaluation is "a pure function" but its location (SQL vs TypeScript) is not stated; H1 needs a decision (recommend SQL so cron-created and action-created Check-ins use one implementation).
- AD-6 rule "only `patients` is imported by all" contradicts the Review Queue (care importing continuity) and Alerts (everything importing notifications); add `notifications` and a `check_ins` reader to the allowed-by-all list.
