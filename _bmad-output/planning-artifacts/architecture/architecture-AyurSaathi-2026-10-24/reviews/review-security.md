# Security and Privacy Review: ARCHITECTURE-SPINE.md

Reviewer lens: ways a developer following the ADs could still leak data or bypass isolation. Context honoured: invented data only; audit log and staff MFA deferred as a hard gate; deployment per clinic; claims in JWT; RLS is the authority.

Verdict: the spine's shape is sound (RLS authority, per-clinic projects, no browser privileged keys), but it is silent on the five or six places where Supabase RLS designs usually leak in practice (security-definer functions, views, storage policy wording, token staleness, auth links, cron/service-role rights), so a compliant developer can still ship a leak.

Legend: NOW = amend the spine before scaffolding (cheap rule, expensive to retrofit). GATE = belongs in the pre-real-data gate list.

## A. Fix in the spine now

### S-1 HIGH (NOW). AD-8: "patient-safe views" will bypass RLS by default
Location: AD-8, last sentence.
Issue: Postgres views run with the owner's rights (typically `postgres`, which bypasses RLS) unless created `WITH (security_invoker = true)`. A view over `notes`/`assessments`/`documents` created the ordinary way returns every clinic's and every patient's rows to any caller who can select it, including `staff_only` rows. This is the single most likely leak, and the view is the very mechanism AD-8 mandates. Also, views in `public` are exposed through the Data API by default, and grants to `anon` are on by default.
Fix: add to AD-8/AD-1: all views are `security_invoker = true`; views live in a non-exposed schema or have `revoke all ... from anon, public` and explicit `grant select ... to authenticated`; the visibility filter is in the view and in the base-table policy (the base-table policy stays the authority, the view only narrows columns). AD-12 adds a test that runs every view as Patient A, Patient B, other-clinic staff and asserts only own `shared` rows. Include views in the "every clinic-owned object has a test" check.

### S-2 HIGH (NOW). AD-3: security-definer helpers and unconstrained function rights
Location: AD-3 (`app.current_role()` etc.), AD-10 (cron database functions).
Issue: nothing says how helper and job functions are defined. Common failure modes: (1) helpers written as `SECURITY DEFINER` without `SET search_path = ''`, allowing search-path hijack; (2) helpers or job functions in an exposed schema, callable by any user as RPC (`/rest/v1/rpc/...`), and by default `EXECUTE` is granted to `PUBLIC`; (3) a definer function that takes `patient_id`/`clinic_id` as an argument and reads across clinics; (4) helpers that read the profile table (rather than the claim) inside a policy, causing recursion, which developers then "fix" with definer functions that skip RLS.
Fix: add a function rule: helpers are `STABLE`, read claims only (`auth.jwt()`), `SECURITY INVOKER`; any `SECURITY DEFINER` function needs a stated reason in the migration, `SET search_path = ''`, fully qualified names, lives in a non-exposed schema (`app_private`), and has `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` then explicit grants. Cron/job functions are in the private schema and never take caller-supplied clinic or patient identifiers from the client. pgTAP check: list all functions in exposed schemas and all definer functions; fail on any not in an allowlist.

### S-3 HIGH (NOW). AD-3: claim staleness after role change or removal
Location: AD-3, "A role change applies at the next token refresh, and the user is signed out on a role change."
Issue: signing out is not revocation. Supabase access tokens stay valid until expiry (default 1 hour, up to the configured maximum) and the JWT is verified locally by `getClaims`, so a demoted or deactivated staff member (or a patient whose episode/clinic link changes) keeps old claims and full access until expiry. Sign-out only deletes the session; an already-issued access token continues to work against PostgREST. Also, `getClaims` on a symmetric-secret project calls Auth, but on asymmetric keys it verifies locally, so no server round trip catches revocation.
Fix: (a) set access-token expiry short (for example 5 to 10 minutes) as an AD value; (b) policies for staff-only and write paths check a live source, not only the claim: either `app.current_role()` joins `profiles` with `active = true` and a `role_version`, or the auth hook stores a `role_version` claim compared against `profiles.role_version`; (c) deactivating a user sets `banned_until`/deletes sessions via an admin script and bumps role_version; (d) the pgTAP suite includes a "demoted user with a still-valid old token" case. Decide which model now because it determines helper shape.

### S-4 HIGH (NOW). AD-11: storage policies and signed URLs under-specified
Location: AD-11.
Issue: "Storage policies mirror table policies" is not implementable as written: storage policies see only the object path/bucket, so a developer must parse the path. Risks: (1) policy checks only `clinic_id` folder and not patient or visibility, so any patient in the clinic can read any other patient's files by guessing a path (UUIDs help, but signed-URL creation by path with the user's token will succeed if the policy allows); (2) `staff_only` documents are not enforced at storage level; (3) "short-lived" is undefined: a signed download URL is a bearer link, works without login, and survives role change; (4) client-supplied filename/extension or content-type trusted (stored XSS or content sniffing from an inline-served file); (5) upload signed URL (`createSignedUploadUrl`) allows overwrite when `upsert` is set; (6) the 15 MB and type limits enforced only in the browser (HEIC conversion happens in browser) are bypassable by calling the API directly.
Fix: state: storage policy must join to `documents` by path/`document_id` and apply the same patient, clinic and visibility checks as the table (not folder-prefix only), with no storage-level write for patients except via a pending-document row they own; download URLs expire in at most 60 seconds, generated per click and never stored or logged (AD-14); uploads: no upsert, bucket-level `file_size_limit` and `allowed_mime_types` configured in migration, server action re-checks the declared type and magic bytes after upload and quarantines on mismatch; serve with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`; extension derived server-side, never from the client. pgTAP bucket tests cover Patient A vs B, staff_only, other clinic, and unauthenticated.

### S-5 HIGH (NOW). Invite, sign-in link and OTP handling are not specified at all
Location: `(public)/` "sign-in, invite" in Structural Seed; AD-5 mentions Send an Invite only for idempotency; Open Question 5.
Issue: the spine says nothing on how invites and magic links/OTP work. Known failures: (1) email security scanners and link previewers (Outlook Safe Links, Gmail, corporate gateways) perform GET on the link and consume a single-use token, locking out the real user, and the usual "fix" is to lengthen expiry or make tokens reusable, which weakens security; (2) an invite that is a bearer link lets whoever has the mail (forwarded or shared inbox, or the forwarded message) take over the account, and the invite link determines `role`/`clinic_id`, so an invite that carries a role or clinic from query parameters is privilege escalation; (3) open sign-up on the Supabase project: anyone can call `/auth/v1/signup` with the public key and create an account; the auth hook might then default them into a role or clinic; (4) enumeration of whether an email is registered via different responses; (5) OTP brute force and unthrottled resend, mail bombing the patient.
Fix: add an AD for auth links: public sign-ups disabled (invite-only; `disable_signup = true`) and the hook defaults to no role and no clinic (deny by default); invite = server-created row (`invites`: hashed token, clinic_id, role, patient_id, expires_at, used_at, created_by) and the role/clinic come only from that row, never from the URL or user metadata (and the hook reads `app_metadata`, never `user_metadata`, which users can edit); the link lands on a page that requires an explicit button click (POST) to redeem so scanner GETs do not consume it, or use a 6-8 digit OTP typed on the device instead of a clickable token; expiry of 24 to 72 hours for invites, 10 minutes for sign-in codes, single use, bound to the invited email; uniform responses for known/unknown email; resend cooldown. Enumerate the Supabase Auth rate limits to set (OTP, email, verify per hour). Redirect URL allowlist set to the clinic's deployment domain only (open redirect after login).

### S-6 MEDIUM-HIGH (NOW). AD-4: service-role key handling is vague, and "server-only scheduled jobs" contradicts the stack
Location: AD-4, AD-10, Structural Seed.
Issue: AD-10 runs jobs as `pg_cron` inside Postgres, which needs no service-role key at all, while AD-4 says the service-role key exists "in server-only scheduled jobs and admin scripts." Which jobs outside the DB hold it? The Vercel project probably gets the key as an environment variable for the "sender" (email delivery) and invite sending (creating auth users requires admin API). That puts a god key in the same runtime as all request handling, so one SSRF/dependency compromise or an accidental import from a client-reachable module reads everything for that clinic. Also: Vercel env vars are visible to everyone with project access, and preview deployments inherit them unless scoped; the per-clinic model multiplies the number of keys.
Fix: rule: service-role key is never set in the Vercel runtime that serves requests. If the sender and invite creation need it, isolate them in a separate server-only module/route (`import 'server-only'`, lint rule banning the import elsewhere) or better a separate Vercel project/Supabase Edge Function with only that secret; scope the variable to Production only (not Preview/Development); no key in preview deployments, which should point at a throwaway Supabase project; secret scanning in CI; documented rotation. Prefer narrow Postgres roles (e.g. a `notification_sender` role with execute on one function) over service-role.

### S-7 MEDIUM (NOW). AD-10: pg_cron jobs run with elevated rights
Location: AD-10.
Issue: `pg_cron` jobs run as the role that scheduled them (usually `postgres`), bypassing RLS. Job functions that create Check-ins and notifications from patient data, if written with caller-supplied params or joining without `clinic_id`, can write cross-patient rows, and a definer function exposed as RPC (see S-2) lets any user trigger it. Notification rows can also carry health content (flag text, medicine names) that then goes out by email.
Fix: job functions live in a private schema, are idempotent, take no client parameters, set `search_path`, and the cron command is just `select app_private.fn()`. Notification payload rule: email body contains no health content, only a generic prompt with a link (put in AD-14 and AD-10). The sender reads the outbox via a narrow role.

### S-8 MEDIUM-HIGH (NOW). Service worker caching (Serwist) can persist health data and leak across users on shared devices
Location: Stack (Serwist), Deferred ("Offline use beyond the app shell").
Issue: nothing constrains what is cached. Default Serwist/Workbox runtime strategies can cache authenticated HTML, RSC payloads, API and signed-URL responses, so a patient's plan or a passport scan persists on disk, survives sign-out, and is visible to the next user of a shared or family phone; caching a signed URL response or document defeats short expiry. Also stale cached pages can show another role's UI after a role change.
Fix: add a rule: the service worker precaches static assets and the offline shell only; `NetworkOnly` for everything under `(patient)`, `(clinic)`, `/api`, server actions, Supabase and storage origins; never cache responses with `Cache-Control: private/no-store` or an `Authorization` or cookie; sign-out clears Cache Storage and unregisters data caches; authenticated pages send `Cache-Control: no-store`. Add a test that lists Cache Storage after an authenticated session and asserts no authenticated route is present.

### S-9 MEDIUM (NOW). Headers, CSP and rate limiting are not mentioned
Location: spine silent; `proxy.ts`, AD-5 (`rate_limited` code exists but nothing produces it).
Issue: no CSP, HSTS, frame-ancestors, referrer policy or permissions policy. For an app rendering patient-entered text, uploaded files and HEIC conversion in the browser (a WASM/worker dependency), the lack of CSP removes the main XSS containment, and a signed-URL in the Referer to a third party leaks a bearer link. `rate_limited` is a result code with no mechanism; Vercel functions are stateless, so in-memory limiters do not work.
Fix: AD addition: `proxy.ts` sets a nonce-based CSP (`default-src 'self'`, `frame-ancestors 'none'`, `connect-src` limited to the clinic's Supabase origin, `object-src 'none'`), HSTS, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` minimal; `img-src` must not allow arbitrary hosts. Rate limiting: say where it lives (Supabase Auth limits for sign-in/OTP/invite; a database-backed counter or Vercel/edge limiter for server actions: invite send, upload sign, check-in submit, login attempts), keyed by user and IP.

## B. Smaller items to fold into the spine now

- S-10 MEDIUM. AD-1/AD-12: "at least one policy" is weak. A permissive `using (true)` policy satisfies it. Require policies to be scoped `to authenticated`, forbid `using (true)`/`anon` grants in review (add a pgTAP lint: no policy with a trivially true expression; anon has no grants on clinic tables), and use `FORCE ROW LEVEL SECURITY` plus `WITH CHECK` on insert/update so a user cannot write a row with another `clinic_id`, or change `clinic_id`/`patient_id`/`visibility` on update (make those columns immutable by trigger or column grants).
- S-11 MEDIUM. AD-2: per-clinic projects reduce cross-clinic risk, but the AD-12 test uses two clinics in one database, which is inconsistent with the deployment model; keep it (defence in depth) but state why. Also state that the JWT `clinic_id` must equal the deployment's own clinic (`app.current_clinic()` also checks against a `clinic` constant), so a token from another clinic's project, if the JWT secret/key were ever shared or reused across projects, is rejected. Require a distinct JWT signing key per project; never copy `.env` between clinics.
- S-12 MEDIUM. Patients versus guardians/shared accounts: AD-3 maps a user to `current_patient()`. The spine does not say what happens for a patient with a companion/family member, or when the same email serves two patients. State "one auth user = one patient" explicitly.
- S-13 MEDIUM. Server actions: AD-5 validates input but not authorization on object ids. State that actions pass ids to queries made as the user (RLS decides) and never use a privileged client to "look up" an object first; and forbid `SECURITY DEFINER` RPC wrappers for convenience (links to S-2). Next.js server actions are public POST endpoints: CSRF protection via same-origin check is built in, but allowed origins config must be pinned to the clinic domain.
- S-14 LOW-MEDIUM. AD-14: add that signed URLs, invite tokens and OTPs are treated as secrets in logs (URL query strings in access logs and Vercel logs), and that error reports must scrub them. Also that `messages`/emails never include health content (see S-7).
- S-15 LOW-MEDIUM. Data residency and processors: Vercel functions run in a region chosen separately from the Supabase India region (set function region to `bom1`), otherwise health data transits and may be logged outside India/EU. The SMTP provider is a third processor receiving patient email addresses. The EU patients bring GDPR transfer questions; record in Deferred that this is a gate item. Sandbox SMTP for the hosted demo must not be a public inbox service.
- S-16 LOW. Supabase project settings absent from the spine: leaked password protection, email confirmation required, JWT expiry, MFA enrolment enabled (so the later gate is a toggle), Data API exposed schemas limited to those intended, `anon` role grants revoked, database not publicly reachable (network restrictions), backups on (PITR) even for the prototype if the demo ever holds anything resembling real data. Add a "project baseline" checklist run by the release routine (AD-13), and run `get_advisors` (security) in CI.
- S-17 LOW. Seed data: AD-13 says invented; also add a guard that seed and demo accounts (with known passwords) cannot be created in any non-prototype project (check an `ENVIRONMENT=prototype` flag in the seed and fail otherwise), so the demo credentials never carry over to a real-data clinic.

## C. Pre-real-data gate list (not for the spine now, but write them down as one list)

Already stated: audit log, staff MFA. Add:
1. Audit log that also covers reads of documents and signed-URL issuance (not only writes), because AD-15 only captures writes through server actions; reads via RLS direct from the browser or via storage are invisible to the "one place".
2. Staff MFA enforced by policy (AAL2 claim required in RLS for staff roles), not just by sign-in UI. Patients: consider OTP-based step-up for documents.
3. Malware scanning, field encryption of passport numbers, retention and erasure (already deferred), plus DPIA/transfer assessment (EU patients, India processing), processor agreements (Supabase, Vercel, SMTP), and breach-notification procedure (72 hours GDPR; DPDP Act obligations in India).
4. Key rotation runbook and a break-glass procedure for the service-role key; secrets in a manager, not only Vercel env.
5. Penetration test or at least a structured RLS review, with an independent re-run of the pgTAP suite against production schema.
6. Backups, restore test, and availability targets for health records; deletion from backups on erasure.
7. Monitoring/alerting for anomalous access (many document downloads, role changes), which depends on the deferred monitoring tools; redaction rules for any error tracking vendor (AD-14).
8. Per-clinic provisioning checklist so the first real clinic is not hand-configured (project baseline in S-16 verified).
9. Review of consent text versions as legal evidence (store which version each patient accepted; immutable once accepted).
10. Account recovery and device-loss procedures for patients (identity proofing before resetting access to health data).
